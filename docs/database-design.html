Data Model · Reference

AttendTrack — Employee Attendance Management System · Microservices

Entity–relationship model for the AttendTrack platform. Each of the three microservices owns one MySQL schema and never reads another's tables — the only column they share is user_id, the stable UUID minted by authservice_db.users and copied outward through the user-registered Kafka event. One real foreign key exists (refresh_tokens → users); every cross-schema link is a logical reference with no database-level constraint.

Relationships

  • Foreign key — enforced by MySQL. Exists only inside one schema: refresh_tokens.user_id → users.id.
  • Logical reference — the same user_id value with no FOREIGN KEY constraint. Every arrow that crosses a service / schema boundary.
  • Update on approve — inside leaveservice_db, approving a leave_request writes back to the matching leave_balance counters.

Column markers

  • PKPrimary key — BIGINT AUTO_INCREMENT on every table.
  • UQUnique constraint. UQ* marks a column that is part of a composite unique (leave_balance (user_id, year)).
  • FKForeign key column — points at another table's primary key within the same schema.
Databases are never cross-queried. Each service connects (JDBC) only to its own schema — authservice_db, attendanceservice_db, leaveservice_db. Identity data (user_id, employee_id, names, department, salary) is replicated into employee_profiles and leave_balance when the user-registered Kafka event is consumed, and into leave_request rows as they are created.
Schema is generated by Hibernate (ddl-auto=update) and mirrored in database/schema.sql; demo rows in database/sample-data.sql. See docs/architecture.html for the runtime / deployment view.
