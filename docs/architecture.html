System Design · Reference

AttendTrack Architecture

End-to-end view of the AttendTrack employee attendance platform: a static browser frontend talking over REST + JWT to three independent Spring Boot services, each with its own MySQL database, loosely coupled through a single Kafka topic. Below the map are the five request flows that carry the product — registration, login, check-in/out, leave application and HR approval.

Request Flows

Each flow is one user action traced through the system. Endpoints and side effects are exact; the small diagram shows the hops, the numbered list is the order they run in.

FLOW 1

Registration

POST /auth/register
  1. Frontend sends POST /auth/register to AuthService with name, email, password, role, department and salary.
  2. AuthService validates, BCrypt-hashes the password, generates the next EMP0xx id and saves the row to authservice_db.
  3. AuthService publishes a user-registered event (payload includes salary) to Kafka and returns 201 Created.
  4. AttendanceService consumes the event and creates an EmployeeProfile in attendanceservice_db.
  5. LeaveService consumes the event and creates a LeaveBalance (pl_total 12, sl_total 6, monthly_salary from the event) in leaveservice_db.
FLOW 2

Login

POST /auth/login
  1. Frontend sends POST /auth/login with email and password to AuthService.
  2. AuthService looks up the user and verifies the password against the stored BCrypt hash (same error for unknown email and wrong password).
  3. On success it generates a JWT access token (1 hour) and a refresh token (24 hours, stored in the DB).
  4. Response returns accessToken, refreshToken, userId, role, employeeId, firstName.
  5. Frontend stores both tokens in localStorage and redirects to the employee or HR dashboard by role.
FLOW 3

Check-in / Check-out

POST /attendance/checkin
  1. Frontend sends POST /attendance/checkin to AttendanceService with the Authorization: Bearer JWT.
  2. AttendanceService validates the JWT locally (shared secret — no call to AuthService).
  3. It checks whether the user has already checked in today; if so it rejects the request.
  4. It saves the attendance row with status PRESENT (before 09:30) or LATE (after) in attendanceservice_db.
  5. Response returns checkInTime and status. Check-out later computes workingHours and the final status.
FLOW 4

Leave Application

POST /leave/apply
  1. Frontend sends POST /leave/apply to LeaveService with leave type, start/end date and reason, plus the Bearer JWT.
  2. LeaveService validates the JWT locally.
  3. It checks the PL / SL balance for the year (accounting for pending requests) — UNPAID is always allowed.
  4. It checks for any overlapping PENDING/APPROVED request, and that the dates are in the future with at least one working day.
  5. If all checks pass it saves the request with status PENDING in leaveservice_db and returns the leave id and day count.
FLOW 5

HR Approves Leave

PUT /leave/hr/approve/{id}
  1. HR frontend sends PUT /leave/hr/approve/{id} to LeaveService with the Bearer JWT.
  2. LeaveService validates the JWT and enforces role = HR (an EMPLOYEE token gets 403).
  3. It confirms the request is still PENDING and re-checks the balance.
  4. It sets the request status to APPROVED and records approved_by.
  5. It deducts the days from the matching LeaveBalance (pl_used / sl_used / unpaid_used) in leaveservice_db.
Deployment: docker compose up --build starts six containers — MySQL, ZooKeeper, Kafka, and the three services — on one bridge network. Each service also runs standalone with ./mvnw spring-boot:run against a local MySQL and Kafka.
